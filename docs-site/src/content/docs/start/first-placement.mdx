Let's place one real card together and then prove why it went to that agent. We'll check the
service, opt in your board, make a card ready, and follow the decision all the way to its outcome.

For this tutorial, SuperDispatch gets a seat in the broadcast booth: it names the pick and explains
the call, but it never claims the card. The chosen agent does that through SuperPipeline.

## What you need

Complete [What you need](/start/what-you-need/) first. You need:

- a SuperPipeline board with a capability-owned stage;
- at least two enabled agents on that board's AgentPod roster with the capability;
- an Accounts service credential with the required scopes; and
- SuperDispatch [running](/run/running-it/).

In the commands below, set `$TOKEN` to the SuperDispatch operator token and `$BOARD` to the full
SuperPipeline board ID, including its `brd_` prefix.

<HeadsUp>
  Keep the operator token private. The operator API returns `401` for a missing or incorrect token.
</HeadsUp>

<Tip>
  The event relay is optional. A `card.ready` delivery triggers placement immediately. Without the
  relay, an opted-in board is checked on the next sweep, every 30 seconds by default. During that
  wait, an agent may claim the card by pull.
</Tip>

## 1. Check SuperDispatch

We start with the smallest useful question: is SuperDispatch awake? Ask the health endpoint. (A
whole tutorial built on a sleeping service would be admirably optimistic.)

```sh
curl http://127.0.0.1:8796/healthz
```

The response is:

```json
{ "ok": true, "service": "superdispatch" }
```

If the request cannot connect, check the service log. A missing or malformed setting prevents
startup; the error names the setting but never its value. Follow [Running it](/run/running-it/) to
correct the setting and start the service before continuing.

There it is: SuperDispatch is running on its default port, and we have a live operator API to work
with.

## 2. Opt the board in

A fresh SuperDispatch watches exactly zero boards, production included. That's on purpose: a
scheduler that starts scheduling the moment you switch it on is a surprise, and nobody wants
surprises in production. So we opt in deliberately:

```sh
curl -X PUT -H "authorization: Bearer $TOKEN" "http://127.0.0.1:8796/v1/boards/$BOARD"
```

The request has no body. The response has this shape:

```json
{
  "board": {
    "boardId": "brd_…",
    "enabled": true,
    "createdAt": "…",
    "updatedAt": "…"
  }
}
```

SuperDispatch now includes the board in every sweep and checks it immediately. It also sets the
board's placement window in SuperPipeline—10 seconds by default.
During that window, a newly ready card is held back from pull so SuperDispatch can place it first.

If the response is `401`, verify `$TOKEN`. If it says the board ID is invalid, set `$BOARD` to the
full ID shown by SuperPipeline and repeat the request.

Your board is now opted in: its first check has started, and every newly ready card gets that
10-second placement window before pull can take it.

## 3. Make a card ready

Now we give the scheduler something worth scheduling. In SuperPipeline, create a card or choose an
existing one, then move it into the capability-owned stage served by the two rostered agents. The
card is ready while it is waiting in that stage, unclaimed, and not otherwise held. No ribbon
cutting is required; changing the stage is enough.

With the relay, the `card.ready` delivery starts placement immediately. Without it, wait for the
next sweep, which runs every 30 seconds by default. If no decision appears after that interval,
confirm that the board is enabled, the card is still waiting in the stage, and at least two enabled
roster agents can service the stage's capability.

You have put a real card on the starting line. SuperDispatch can now filter the candidates, rank
the eligible ones, and request a hold for its choice.

## 4. Read why that agent was chosen

We have a pick; now let's ask the broadcast booth for the replay. Read the board's latest
decisions, newest first:

```sh
curl -H "authorization: Bearer $TOKEN" "http://127.0.0.1:8796/v1/decisions?board=$BOARD&limit=20"
```

Find the row whose `cardId` matches your card. These fields explain the placement:

| Field | Meaning |
|---|---|
| `chosen` | The agent SuperDispatch selected, or `null` when it selected nobody |
| `tier` | The ladder position as `{ name, step }`; the first placement is `{ "name": "winner", "step": 1 }` |
| `policy` | The ranking policy; the fixed formula is `idle-stage-success-lru@3` |
| `candidates` | Every candidate considered, with its filter results and score |
| `reservation` | `{ reservedUntil }` when SuperPipeline accepted the hold; otherwise `null` |
| `reservationRefused` | SuperPipeline's refusal code, or `null` |
| `outcome` | `{ status, by, at }` after settlement; otherwise `null` |

For an agent that was not chosen, inspect `filters`. A failed filter includes its reason. For
example, `not-idle` means the agent already has work in hand, while `capability-missing` means the
stage asks for a capability the agent does not have. [Candidates and filters](/placement/filters/)
lists every reason code.

For each agent that passed every filter, inspect `score`. The highest `total` wins; `terms` records
the values that established the order. The decision record keeps receipts, which is considerably
more useful than a confident shrug.

If there is no row for the card, use the checks in step 3. If the decision's `reason` is
`one-candidate`, add a second eligible agent to the board's roster or leave the card to normal
pull; SuperDispatch does not choose when there is only one candidate.

You can now name the chosen agent and show your work: every filter result and score term is in the
record, so nobody has to reconstruct the choice from the eventual claim.

## 5. Follow the outcome

Choosing is only half the story, so we come back on a later pass to see what actually happened.
Yes, we're refreshing a query for the ending; even schedulers get a tiny cliffhanger. Run the same
query again:

```sh
curl -H "authorization: Bearer $TOKEN" "http://127.0.0.1:8796/v1/decisions?board=$BOARD&limit=20"
```

Read `outcome.status` on your card's decision:

| Status | Meaning |
|---|---|
| `claimed` | The chosen agent claimed the card |
| `claimed-by-other` | Another agent claimed it after the hold lapsed, or an agent outside the roster claimed it |
| `expired` | The hold lapsed while the card still waited |
| `superseded` | A person moved or archived the card before a claim |
| `not-reserved` | SuperPipeline refused the hold, so no reservation was made |

The winner's hold lasts 60 seconds by default. If it expires, SuperDispatch can hold the card for
runner-ups one at a time for 30 seconds each. After the configured ladder is exhausted, the card is
open to any matching agent. Each hold attempt has its own decision; see
[Holds, tiers and fairness](/placement/holds-and-tiers/).

<HeadsUp>
  The agent claims the card through SuperPipeline. SuperDispatch only chooses an agent, requests a
  temporary hold, and records the decision. If SuperDispatch stops, its holds lapse and agents
  continue to claim by pull.
</HeadsUp>

You can now see how the placement ended: the chosen agent claimed, another agent claimed, the hold
expired, the card moved, or the reservation was refused.

## 6. Opt out when you are finished

We made a placement, explained it, and followed the result. Now we'll put the lab back the way we
found it—future you has enough mysteries already. To stop placing cards on this board, disable it:

```sh
curl -X DELETE -H "authorization: Bearer $TOKEN" "http://127.0.0.1:8796/v1/boards/$BOARD"
```

The board record and its decisions remain readable. Existing holds lapse on their own, and the
board's placement window returns to zero. A later `PUT` enables the same board again.

The board is quiet again: SuperDispatch will not place new cards there, and your decision history
is still available whenever you need it.

The broadcast is over: you have the placement, the reason, and the outcome. The agent did the
claiming; SuperDispatch can take off the headset.
